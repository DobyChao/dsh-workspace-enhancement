## I2. SSH 工作区内的终端/文件系统按对应系统唤起（2026-08-23 记录）

- **用户原话要点**：「在 ssh workspace 里打开的终端/文件系统，应该根据对应的系统唤起。
  例如终端环境就直接到服务器里了（有点像 vscode 远程开发的终端）」。
- 涉及面：会话级派生体验——在远程工作区中打开终端工具时，PTY 应落在**该连接对应的
  服务器**（引擎已支持：ctx.subprocess 的 spawnTerminal 走 SSH 通道；需确认「打开终端」
  的入口/工具是否携带了会话 cwd 的 ssh:// 路由语义 → 已有 ssh://<id>/<path> 路由机制，
  理论上终端已经在服务器上，重点在验证/补齐入口路径）；文件系统同理（ctx.fs 已透明）。
- 很像 VSCode Remote-SSH 的终端体验；可能只需「确认+打磨」而非新造轮子。
- 状态：待需求确认（具体是哪些入口的终端/文件系统尚未落到远程）。

## I3. 一个 Session 允许多工作区 + 焦点工作区 + 逐工作区权限（2026-08-23 记录）

- **用户原话要点**：一个 session 添加多个工作区（有**焦点工作区**，可以是远程的）；
  每个工作区可分别配置权限（「不知道能不能搞」）。
- 涉及面：DSH core 的 session/workspace 模型当前是「1 session → 1 cwd/workspace」；
  多工作区需要 host 侧扩展（焦点切换、多 root 的 fs/exec 路由），且与官方
  workspace 注册表/session 头字段可能冲突或需要上游支持。
- 权限维度候选：只读/读写、允许的命令白名单、是否允许网络/装包、每工作区独立。
- 状态：待需求确认（可行性需先做 core 模型侦察——是否属于「扩展还是改 core」）。

## I4. 焦点工作区为远程时，保证模型知道自己需要在远程工作（2026-08-23 记录）

- **用户原话要点**：焦点为远程的工作区要有机制保证模型知道自己在远程工作。
- 涉及面：系统提示注入（现已注入一行「当前 remote: user@host:/path」）+ 工具使用引导；
  可以在焦点切换时显式强调「当前在远程 X，命令/文件操作走远程」；考虑与 I3 焦点工作区
  联动（模型误导/误用本地路径是风险点）。
- 状态：待需求确认（机制候选：系统提示增强 + 状态注入 + 工具层提示）。
