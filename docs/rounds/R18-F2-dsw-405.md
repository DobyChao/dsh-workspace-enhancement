## 0. 结论速览

| 问题 | 判定 |
|---|---|
| `/dsw` 为什么是 **405** 而不是 404/403？ | **405 由 SPA 兜底位回答**：`dsh-host-frontend-static` 的 `registerFallback` 对**任何非 GET/HEAD** 请求直接 `writeHead(405)`（无 body）——405 恰好等于「**没有任何具名路由匹配到 `/dsw`**」，不是方法权限问题（§3） |
| `dsh-host-webserver@0.1.5-rc.2` 的 `kind:"prefix"` **匹配语义变了**吗？ | **没有变**。`register` / `match` / `registerFallback` 在 `0.1.5-rc.2` 与 `0.1.2-rc.1` 上**逐符号等价**；t3 §13.2 的这条猜测**被排除**（§4） |
| 真正的根因是什么？ | **`dsh-client-connection` 自己的 `inject` 变了**：`register(owner, …)` 末行读 `owner.webServer`，而 `owner` 是 **Connection 服务自己的 ctx**；该包在 0.1.2-rc.1 声明 `["webServer","credentials"]`，0.1.5 只剩 `["credentials"]` ⇒ **任何调用者**调用 `connection.rpc.handle` 都会抛 `cannot get property "webServer" without inject`，**注册从未发生**（§5） |
| 与 F1（启动崩溃）是什么关系？ | **同一个根因的两层症状**：0.1.2-rc.1 上抛错发生在**行 fiber**，整棵 plugin tree 加载失败（F1）；t11 把挂载放进 `ctx.inject(['webServer'], …)` 后，抛错发生在**子 fiber**（Cordis 非致命化）⇒ 宿主能启动（F1 解决），但 `/dsw` **仍未注册**（F2）（§5.3） |
| 修好了吗？ | **仓库内未修**（代码不属 t12）。但**候选 A 已在构建副本上实测修复**：rc.2 / rc.1 / legacy 三家族 `POST /dsw/connections.list → 200` 且 JSON 正确（§6）。两条候选供裁决（§7） |
| 有没有用「改路由名 / 绕开 `/dsw` / 放宽断言」蒙混？ | **没有**。候选 A 保持路径 `/dsw` 与**已发布客户端半的信封协议**不变；断言用的是 t11 哨兵的**严格通道探测**（`POST /dsw/connections.list` 必须 200 + `result.ok=true`） |

**一句话**：405 不是 webserver 路由语义变了，而是**我们依赖的那条上游 API（`connection.rpc.handle`）在 0.1.5 上被自己的 `inject` 变更废掉了**；
上游自己挂 `/api` 是**直接** `webCtx.webServer.register(route)`，其余包走 `connection.fetch.register` / `connection.rpc.intercept`——都只碰 `owner.effect`，不碰 `owner.webServer`。
把挂载改成「自己有 `webServer` 的上下文里直挂前缀路由」即可在**三家族**同时成立（§6 已实测）。

## 3. 405 是谁回答的（兜底位机制）

`dsh-host-webserver` 的请求处理：先查具名路由（exact 表 → prefix 表），未命中则交给**兜底位**（fallback）：

```js
// dsh-host-webserver@0.1.5-rc.2/lib/index.js —— 符号：handle() / match() / registerFallback()
const route = this.match(rawPath)
if (route !== void 0) { await route.handler(req, res); return }
const fallback = this.fallback
if (fallback === void 0) { res.writeHead(404); res.end(); return }
await fallback(req, res)
```

兜底位的**唯一占用者**是前端静态行：

```js
// dsh-host-frontend-static@0.1.5-rc.2/lib/index.js —— 符号：registerFallback 回调
ctx.effect(() => ctx.webServer.registerFallback(async (req, res) => {
  if (req.method !== "GET" && req.method !== "HEAD") { res.writeHead(405); res.end(); return }   // ← 405，无 body
  await serveStatic(decodeURIComponent(rawPath), res, distRoot, distIndex, …)
}), "frontend-static: fallback seat")
```

⇒ **观察到的状态码分布正是这两行的指纹**：`POST /dsw/connections.list → 405`（非 GET/HEAD）＋`GET /dsw → 404`（GET 走静态、无此文件）。
`0.1.2-rc.1` 的同一文件是**同一规则**（`registerFallback` 内 `req.method !== "GET" && req.method !== "HEAD" → writeHead(405)`），
所以**错误映射两代一致**——差异只可能在「路由是否被注册」。

实测佐证（§6.3 原始探针，405 那行的 body 是空的，与 `writeHead(405); res.end()` 一致）：

```
repo-rc2 : redeem=303 post=|HTTP 405
```

## 4. 假说判定：webserver 的 prefix 匹配语义**没有**变化

| 符号 | `dsh-host-webserver@0.1.5-rc.2` | `dsh-host-webserver@0.1.2-rc.1` | 判定 |
|---|---|---|---|
| `register(route)` | 按 `route.kind === "exact"` 选表，重复 `(kind, path)` 抛错，返回删除 disposer | 同形同语义 | **等价** |
| `match(pathname)` | 先 exact 表；再 prefix 表，`pathname !== prefix && !pathname.startsWith(prefix + "/")` 则跳过，最长前缀胜出 | 同形同语义 | **等价** |
| `registerFallback(handler)` | 单占位，二次注册抛错 | 同形 | **等价** |
| `[Service.init]` 请求分发 | 见 §3 片段（`match` → `fallback` → 404/405） | 同形 | **等价** |

⇒ **t3 §13.2 建议②（prefix 匹配语义变化）排除**。`kind:"prefix"` + `path:"/dsw"` 在 0.1.5 上依然能匹配 `/dsw/connections.list`；
§6 的实验进一步**直接证实**：同一个 rc.2 宿主里，只要路由真的被注册，`POST /dsw/connections.list` 立刻 200。

## 5. 根因：`connection.rpc.handle` 在 0.1.5 上被自己的 `inject` 废掉

### 5.1 符号级对照（同一条 API，两代家族的差异只有 `inject`）

| 符号（`dsh-client-connection/lib/index.js`） | `0.1.5-rc.2` | `0.1.2-rc.1` | 差异 |
|---|---|---|---|
| `get rpc()` | `:540`，`const owner = this.ctx`（`:541`） | `:517`，`const owner = this.ctx`（`:518`） | 无 |
| `register(owner, channel, handler)` | `:602` | `:572` | 无 |
| 路由形状 | `{ kind: "prefix", path: channel, handler }` | 同 | 无 |
| 注册语句 | `owner.effect(() => owner.webServer.register(route), …)`（`:618`） | 同（`:588`） | 无 |
| **`const inject`** | **`["credentials"]`**（`:736`） | **`["webServer", "credentials"]`**（`:681`） | **唯一差异** |
| `requestRejection(request)`（公开方法） | `:553` | `:530` | 无 |

**机理**：`owner` 取的是 `this.ctx`，即 **Connection 服务自身所在的 ctx**，不是调用者上下文
（这也解释了 t11 的实测：把 `webServer` 加进我们的顶层 `inject` 无用，包进 `ctx.inject(['webServer'], …)` 也只能让失败非致命）。
`owner.webServer` 是一次**属性读取**，Cordis 的 `ReflectService` 在该 ctx 未声明 `webServer` 时直接抛
`cannot get property "webServer" without inject` ——**语句在 `register` 内、`webServer.register(route)` 之前就中断了**，
所以不是「注册了但没生效」，而是**从未注册**。

### 5.2 实测（两处独立证据）

1. **回调确实运行、抛出确切错误**（t11 的临时文件探测，探针已移除）：
   `mount callback threw: Error: cannot get property "webServer" without inject`
2. **未修复构建的真 boot 崩溃**（t11 负向对照，构建副本只还原 pre-fix 两行）：
   `FAIL the host never printed a listening URL within 45000ms` / `host exit code=1` /
   `[cause] Error: failed to apply loader entry ssh-web-channel (dsh-workspace-enhancement/web): cannot get property "webServer" without inject`，
   栈帧落在 `unfixed/lib/web.js:521`（该副本的挂载点）→ `dsh-client-connection/lib/index.js:618`。

### 5.3 为什么 F1「修好」而 F2 仍然坏（同根两层）

`ctx.inject(['webServer'], (webCtx) => { … })` 把挂载放进了**子 fiber**：抛错仍会发生，但 Cordis 把**子 fiber 的失败非致命化**
（tree 加载成功、宿主继续跑）⇒ 症状从「整个宿主起不来」退化为「`/dsw` 静默不存在」。
t3 §11 的「实验 B 启动成功」为真，但**它不是修复，而是把致命失败装进子 fiber**（t11 已独立证伪）。

### 5.4 旁证：0.1.5 全树**没有**任何包调用 `rpc.handle`

| 检索 | `0.1.5-rc.2` | `0.1.5-rc.1` | `0.1.2-rc.1` |
|---|---|---|---|
| `rpc.handle(` 调用点（全部 `@deepseek-ai/*/lib/*.js`） | **0** | **0** | **0** |
| `handle: (channel, handler)` 定义点 | 仅 `dsh-client-connection` | 仅同名包 | 仅同名包 |

上游自己挂通道的三种写法（都不碰 `owner.webServer`）：

- `dsh-client-connection` 自己的 `/api` 路由：`ctx.inject(["webServer"], webCtx => … webCtx.webServer.register(route) …)` ——**直挂**；
- `dsh-api-gateway@0.1.5-rc.2`：`connectionCtx.connection.rpc.intercept("/api", matches, handler)`（`inject(["connection"])`）；
- `dsh-client-file-upload@0.1.5-rc.2`：`ctx.connection.fetch.register({ path, methods, fetch })`（`static inject = ["agents","attachments","commands","connection"]`，**不含 webServer**）。

⇒ 我们是**唯一**使用 `rpc.handle` 的调用方；该 API 在 0.1.5 上属于「已发布但被自家 inject 变更废掉」的状态。

## 6. 实测修复：候选 A（在**构建副本**上，仓库代码未改）

### 6.1 修法摘要（精确到可照抄）

把 t11 的挂载块（`ctx.inject(['webServer'], webCtx => webCtx.connection.rpc.handle('/dsw', dispatch, …))`）
换成**直挂前缀路由**，并在 handler 内保留上游的两个语义：loopback/Host 栅栏用**公开方法** `connection.requestRejection(req)`，
信封维持已发布客户端半的协议：

```ts
ctx.inject(['connection', 'webServer'], (webCtx) => {
  webCtx.effect(() => webCtx.webServer.register({
    kind: 'prefix',
    path: '/dsw',
    handler: async (req, res) => {
      const rejection = webCtx.connection.requestRejection(req)
      if (rejection !== undefined) { res.writeHead(rejection); res.end(rejection === 401 ? 'unauthorized' : 'forbidden'); return }
      // 读取 JSON 信封 {type:"client-request", rpcId, method, payload} → dispatch → {type:"server-response", rpcId, result}
    },
  }), 'dsw: /dsw rpc channel')
})
```

## 7. 两条候选修法（供 captain 裁决）

| | **A. 宿主半直挂前缀路由** | **B. 走官方共享 `/api` 通道** |
|---|---|---|
| 宿主改动 | `ctx.inject(['connection','webServer'], … webCtx.webServer.register({kind:'prefix',path:'/dsw',handler}))` | `ctx.inject(['connection'], c => c.connection.rpc.intercept('/api', endpoint => claims, dispatch))`（`dsh-api-gateway` 同款） |
| 客户端改动 | **零**（协议与 URL 不变，已发布客户端半照旧可用） | 需要：`/dsw/<endpoint>` → `/api/<endpoint>`（`src/client/**`） |
| 语义正确性 | 复刻上游桥接（信封、栅栏）；需自行保证与 `rpcFetchHandler`/`bridge` 等价 | 完全走上游通道（拦截器是官方扩展点），无复刻 |
| 主要风险 | 上游改信封/流式语义时我们要跟（漂移）；`requestBody` 模式、SSE/流式、错误码映射需对齐 | 与别的 `/api` 消费者共享命名空间（`matches` 必须精确 claim），且客户端半要同步发版 |
| 实测状态 | **已实测**：rc.2 / rc.1 / legacy 全 200（§6） | **未实测**（客户端半不在 t12 inScope；宿主侧可另行验证） |
| 我的建议 | 若要**保持已发布客户端兼容**（本 PR 的现状）→ A；若愿同步改客户端且要最正的语义 → B（并把 A 作为回退） |
