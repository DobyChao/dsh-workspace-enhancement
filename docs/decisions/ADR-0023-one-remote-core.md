# ADR-0023: 远端「一个核心」——把分项安装收敛为单一可校验产物

- 状态: accepted（方向已由用户拍板；实现未排期）
- 日期: 2026-09-13
- 范围: 产品方向与远面前置条件；载体是 `REQ-I5`（本 ADR 为其范围依据）。落地时会触及
  `src/registry.ts`（核心版本/健康面）、`src/exec-tools.ts`（`remoteEnvProbe` 语义）、
  `src/model-prompts.ts`（模型面提示措辞）、`src/remote-sandbox.ts`（runner 来源）、
  以及部署/校验/升级路径（新增模块）
- 关联: 承接 **REQ-I9**（其 runner 契约成为核心 runner 的契约）、**ADR-0022 §2.7**（fs 写面不被 spawn 围栏覆盖，
  完全体要由核心的远端 fs 服务解决）、**AUDIT-6**（无核心时退化为审批门 + 低权用户）；
  收尾 `REQ-I12` ④（`remoteSandboxRunner` 死字段由核心统一定位）

## 0. 结论

远端的**唯一人工前置**是「部署一个核心」。今天插件分项要求的三样东西——`pwsh`（Windows 目标的
PowerShell 工具）、`ripgrep`（glob/search）、`bwrap`（REQ-I9 的执行围栏 runner）——**都是这同一个核心的
组成部分**，不再作为「请用户逐包安装」的清单。核心是一个**单一、可校验的产物**，由插件负责上传、校验、
版本探测与升级。

用户 2026-09-13 拍板（原话）：「bwrap 和部署核心差不多」「之前要求用户在远程装 rg 我感觉就比较难受了」
「我感觉就最多装一个核心好了」。

## 1. 背景：分项前置已经变成摩擦

- **要求分散且措辞过时**：同一条「远端需装 pwsh / ripgrep」写在 `SECURITY.md`、`docs/architecture.md` §8、
  `docs/testing.md`、`docs/ROADMAP.md`、`CHANGELOG.md` 五处；**模型面提示**（`src/model-prompts.ts` 的
  `envMissing`）甚至仍在教用户 `sudo apt-get install ripgrep`。REQ-I9 之后还要再加一项 `bwrap`。
- **每一项都在把宿主的工程问题推给用户**：`rg` 是官方 glob/search 工具在远端的事实依赖；`bwrap` 是围栏的
  runner；`pwsh` 是 Windows 目标的执行面。三者都不是用户「想装」的东西，而是**插件要跑起来就得有**的东西。
- **REQ-I9 已经证明「接缝可替换、围栏可自管」**：包装点、正向探针、fail-closed 语义都已落地并被评审 pass
  （ADR-0022）。剩下唯一未解的是「runner 从哪来」——这正是核心要回答的问题。

## 2. 决定

1. **产品目标 = C 路线（部署一个核心）**，`REQ-I5` 由「远期愿景备忘」升格为其载体（范围与验收见 backlog）；
   本 ADR 是它的范围依据。**分项安装清单随之作废**：五处文档 + 模型提示统一改为「核心是否就位」的语义。
2. **核心至少提供三件东西**，按优先级：
   1. **沙箱 runner**（最高优先）——REQ-I9 的接缝由它满足。核心里自带 runner（可以是静态 `bwrap`，也可以是
      **不依赖 userns 的自研实现**）⇒ **G1 那道「远端能不能以登录用户跑 bwrap」的门从用户问题变成核心内部问题**；
   2. **`rg`（或等价搜索能力）**——glob/search 的事实依赖，随核心一起就位；
   3. **完全体：远端 fs 服务**——这才解决 `ADR-0022 §2.7` 的诚实缺口（SFTP 写面围不住）。**这一件可以后置**，
      但它决定了「围栏」能不能从「只围命令」升级到「围住整个远端执行面」。
3. **一个产物，可校验**：核心是单一文件/工件（静态二进制或单文件包），带**版本 + 校验和**；插件负责
   上传、校验、版本探测与升级。**插件不代跑包管理器**（`apt-get` 需要 root、依赖发行版、且把供应链问题
   转嫁给远端仓库）——这是本 ADR 与「自动装包」方案的分界。
4. **部署位置与权限**：默认部署到用户域（`~/.dsh-core/` 之类的**登录用户可写路径**），因此**不需要 root**；
   需要 root 的形态（系统级安装、需要特权的 runner）**不在 v1 范围**。
5. **退路如实**（不给假保证）：核心在目标主机跑不起来时（架构不符、无 userns 且自研 runner 也失败、
   登录用户不可写、容器限制），**明确退化为「审批门（ADR-0020）+ 低权用户/容器（路线 C）」**
   并在机器健康面如实报告，**不假装有围栏**。
6. **与现有机制的关系**：
   - `remoteSandboxRunner`（今天的死配置面）在核心落地后由**核心自己的路径**决定，不再由用户填；
   - `remoteEnvProbe` 的语义从「缺什么装什么」变为「核心是否就位 / 版本是否满足 / 能力是否可用」；
   - REQ-I9 的 runner 契约（`<runner> <profile args> -- <argv>`、正向功能探针、`SANDBOX_UNAVAILABLE`
     fail-closed、未包装 argv 进审批门）**原样成为核心 runner 的契约**——核心换的是「runner 从哪来」，
     不是「围栏怎么工作」。
7. **不做**：不在远端跑通用包管理器；不代理 npm/pip 之类的语言生态；不把整个宿主 DSH 搬过去
   （`REQ-I5` 的原意只要求「部分能力」）；不做需要 root 的系统级安装。

## 3. 代价与风险

- **供应链成为新的信任根**：核心二进制从哪来、谁签名、如何校验、如何升级，是本方向**最大的新风险面**；
  在把「用户装包」换成「插件推二进制」之后，插件的发布与校验流程必须覆盖这个产物（否则风险只是换了个地方）。
- **架构覆盖**：x86_64 / aarch64（以及未来的其它目标）需要分别构建与验证；只支持其中一种必须**明说**。
- **多版本共存与升级**：远端可能同时存在多个核心版本（多台机器、多会话），需要「版本探测 + 按机器记录 +
  升级不打断会话」的设计。
- **核心自身在围栏内的角色**：核心是**被围栏对象的一部分**（它启动进程），又是**围栏的执行者**——
  它的稳定性直接决定远端能否执行命令（今天 `SANDBOX_UNAVAILABLE` 的语义务必保持 fail-closed，不能因为
  「核心挂了」而静默裸跑）。
- **ADR-0022 的边界不会自动消失**：在核心的远端 fs 服务落地之前，**fs 写面仍然不被围栏覆盖**；
  文档与提示词不得提前宣称「已围栏」。

## 4. 验收（核心落地那轮的验收口径，供 backlog 引用）

1. **一个产物**：一条命令/一次面板操作即可把核心部署到远端用户域，全过程**不需要 root**；
2. **可校验**：核心带版本与校验和，校验失败即拒绝使用并如实报错；
3. **能力面**：部署后 `glob`/search 不再需要用户预装 `rg`；`remoteSandbox: read-only|workspace-write`
   在核心自带 runner 上**原生可用**（不再要求用户预装系统 `bwrap`）；
4. **fail-closed 不变**：核心缺失/校验失败/runner 不可用 ⇒ 拒绝执行，绝不裸跑（沿用 REQ-I9 的断言口径，
   含「命令从未执行」的证明）；
5. **退路可证**：核心跑不起来的主机上有明确、可执行的错误与降级说明；
6. **文档收敛**：`SECURITY.md` / `docs/architecture.md` / `docs/testing.md` / `docs/ROADMAP.md` /
   `CHANGELOG.md` 与**模型面提示**中的分项安装清单全部替换为「核心」语义（本 ADR 落地时一次性收口）。
